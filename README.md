# UPI Scam & Mule Detection (PBL-III, AIM3170)

A system that scores every UPI payment, explains every alert in plain English, and maps the mule accounts that move stolen money. It is trained and **measured** on labelled, UPI-style simulated data.

> **Status:** working prototype on simulated data. Every number in this README comes from `RESULTS.md`, which `train_and_evaluate.py` regenerates.

## Headline results (unseen test week)

| | Original model (Oct 2026) | Hand-written rules | **This system (hybrid)** |
|---|---|---|---|
| PR-AUC | 0.011 | 0.322 | **0.957** |
| Fraud caught when analysts review 2% of payments | 0.8% | 45.3% | **86.1%** |
| Share of those alerts that are real fraud | 0.3% | 47.2% | **95.7%** |
| False alerts on a week of normal-only payments | 89% (old demo set) | – | **1.4%** |

What changed and why it matters:
- **The model is trained on data where its features actually vary.** The October model was trained on PaySim-style data where the device, velocity and chain features were (almost) always zero. 10 of its 30 features were never used by any tree, and it flagged 89% of normal payments.
- **The ablation proves each part helps.** Random Forest PR-AUC rises from 0.72 (amount only) to 0.87 (+ behaviour), 0.89 (+ device) and **0.96 (+ graph money-flow)**.
- **The weaknesses are tested and reported, not hidden.** When a scam type is missing from training, recall drops sharply (e.g. SIM swap: 76% when seen, 24% when unseen). The Isolation Forest *on its own* still catches 86% of unseen SIM swaps, but the hybrid does not yet keep that strength — an open problem (RESULTS.md, section 5).

## Quick start

```bash
source .venv/bin/activate          # your existing environment
pip install -r requirements.txt    # adds django and networkx; keeps scikit-learn at 1.9.1

python web/manage.py runserver     # website -> http://127.0.0.1:8000  (or double-click run_dashboard.command)
python tests/test_pipeline.py      # 11 model tests: leakage, accuracy, explanations, rings
python tests/test_web.py           # 3 website tests: every page, settings, upload checks
python realtime_demo.py            # score payments one at a time, print alerts + reasons
python train_and_evaluate.py       # retrain everything and rewrite RESULTS.md (~10 min)
```

In the website, open **Normal activity only** first: alerts should be rare and no mule ring should appear. Then open **Scams and mule accounts** or **Deep mule rings** to see scams, reasons and rings.

### The website (Django)

| Page | What it is for |
|---|---|
| Load payments | Open a labelled demo week or upload a CSV (validated before scoring) |
| Overview | Every payment plotted by fraud score, key numbers, accuracy when labels exist |
| Alert queue | Highest score first, with the top three reasons; filter, search, sort, page |
| Payment detail | Score gauge, reasons, "what moved the score" chart, sender's and receiver's other payments |
| Mule rings | Interactive money-flow graph (NetworkX + vis-network) and the ring's payment trail |
| How well it works | Model comparison, ablation, unseen scams, ring escalation, limits |

The alert rule (cost-based or analyst capacity, plus ring escalation) can be changed from any page. No database is needed. Charts, the graph library and fonts are bundled, so the site works offline. The older Streamlit dashboard still runs with `streamlit run fraud_detection_app/app.py`.

## How it works

```
payment ─► feature engine (state per account, past only) ─► 31 features
                                                            ├─► Isolation Forest ─► anomaly score ─┐
                                                            └──────────────────────────────────────┴─► Random Forest ─► fraud score 0–100
fraud score ─► threshold (cost-based or analyst budget) ─► alert + top-3 reasons
alerts in a batch ─► NetworkX money-flow graph ─► mule rings ─► escalate fast pass-through payments in rings
```

**Features (31, in 4 groups; full list in `feature_engineering.py`)**
- *Amount & context*: amount, share of balance sent, balances, hour, night, P2M vs P2P, collect request
- *Behaviour & velocity*: sender history, payments in last 1h/24h, minutes since last payment, amount vs the sender's usual, new receiver, new receivers in 24h, night habit, deviation from usual hour
- *Device*: device changed, never-seen device, hours since change, ₹ sent since change
- *Graph money-flow*: receiver fan-in in 24h, receiver inflow, burst of new payers, sender's own inflow in last 60 min, share of that inflow being passed on, minutes since inflow, **hop depth** (A→B→C…), distinct payers of the sender

All features use only payments **before** the current one. The batch path and the real-time path are the same code. Tests check both properties. Scoring a single payment in real time takes about **0.9 ms** (median; 1.4 ms at the 99th percentile). `fast_models.py` walks all trees at once with NumPy and gives exactly the same scores as scikit-learn.

**Why a hybrid?** The Random Forest learns known scam patterns and is by far the most accurate. The Isolation Forest score adds a "this looks unusual" signal that does not depend on labels. At the same alert budget, the hybrid beats the plain Random Forest on 4 of 5 scam types it never saw, and gives better precision at the chosen threshold. Isolation Forest alone is weak overall but catches 86% of unseen SIM swaps. Running it as a separate safety net with its own small alert budget is the obvious next step.

**Thresholds like a bank.** The alert threshold is chosen on a separate validation week to minimise *₹ of fraud missed + ₹200 per alert reviewed*. The review cost is an assumption, and RESULTS.md shows how the threshold moves for ₹50–₹5,000. The dashboard can instead alert on a fixed share of payments (analyst capacity).

**Reasons for every alert.** Each fraud score is split exactly into contributions per feature (tree-path attribution). The top three become sentences such as *"Passes on 94% of money received in the last hour"*. On the top test alerts the top reason matches SHAP in 82.0% of cases.

**Graph layer.** Graph money-flow features carry most of the graph's value inside the model (ablation). `mule_rings.py` then builds a NetworkX graph of the batch, links alerted payments and fast pass-throughs, and reports rings: groups of 3+ accounts with at least 5 alerted pass-through payments. Escalating pass-through payments inside rings lowered the test week's total cost from ₹3.17 lakh to ₹1.79 lakh.

## Data and UPI rules used by the simulator

`upi_simulator.py` creates customers with their own spending habits, merchants, salary and rent. It also creates legitimate behaviour that looks suspicious: night owls, genuine phone changes, two-device users, family members who pass money on, and informal sellers paid by many people. Five scam types are injected: QR "receive money" scams, fake refund calls, screen-sharing app drains, SIM swaps, and fake-merchant collect requests. Stolen money flows through mule rings with 1–3 layers. Account IDs give no hint of the label.

UPI rules applied, as reported in public sources (verify before quoting as official):
- P2P collect requests discontinued from 1 Oct 2025, so collect fraud is modelled through merchant collect ([Business Today, Aug 2025](https://www.businesstoday.in/amp/personal-finance/banking/story/npci-to-tighten-upi-rules-peer-to-peer-collect-feature-to-end-in-october-489244-2025-08-13))
- ₹1 lakh per transaction for normal payments; up to ₹5 lakh for some merchant categories from 15 Sep 2025 ([Business Today, Sep 2025](https://www.businesstoday.in/amp/personal-finance/banking/story/npci-to-increase-upi-transaction-limits-for-high-value-payments-from-sept-15-check-updated-limits-493278-2025-09-09))
- ₹5,000 total in the first 24 hours after a new registration, and about 20 payments per day ([Razorpay guide](https://razorpay.com/blog/upi-transaction-limit-per-day/))

## Limitations

- All results are on simulated data. They show the method works and how its parts compare. They do not predict performance at a real bank.
- Fraud is over-represented (about 2% of payments) so that models see enough examples. At real-world fraud rates, precision would be lower.
- The supervised model is much weaker on scam types it never saw (RESULTS.md, section 5).
- The first 48 hours of an uploaded file have no history, so they are marked "warm-up" and not used for metrics. A real deployment would keep history in a feature store.
- Ring detection uses the whole batch, so it is an investigation tool, not a real-time decision.
